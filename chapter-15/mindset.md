# 第15章 从传统工程师到 Agent 工程师的思维转型

## 本章概览

本章讨论从传统软件工程思维到 Agent 原生工程思维的转型。这不是技术栈的切换，而是对"谁编写代码"和"如何验证代码"这两个根本问题的重新回答。claw-code 的架构设计反映了一种新的工程范式：人类负责意图和验证，Agent 负责实现和迭代，系统负责约束和审计。

## 15.1 从"写代码"到"写意图"

传统工程师的工作流是：理解需求 → 设计方案 → 编写代码 → 测试验证 → 交付。Agent 工程师的工作流是：表达意图 → 观察 Agent 执行 → 干预偏差 → 验证结果。代码不再是手工产物，而是意图的自动展开。

这种转变对工程师的要求不是降低，而是转移。传统工程师需要精确记忆 API 签名和语言语法，Agent 工程师需要精确表达边界条件和异常场景。claw-code 的权限系统（第8章）和钩子系统（第9章）就是为这种转移设计的：权限规则是人类表达的安全边界，钩子是人工干预的自动触发器。

`PermissionRule` 的语法 `"bash(git:*)"` 是一种意图表达——"所有 git 命令自动允许，其他 bash 命令需要确认"。这比传统的访问控制列表（ACL）更抽象，更接近自然语言，但又有明确的机器可解析语义。工程师需要学习这种"半结构化意图"的表达方式。

## 15.2 从"确定性"到"可观测性"

传统软件工程追求确定性——给定输入必然产生预期输出。Agent 系统本质是非确定性的——同样的提示可能产生不同的代码，模型的行为随版本更新而变化。工程思维需要从"确保正确"转向"确保可观测和可纠正"。

claw-code 的 `SessionHeartbeat`（第10章）和 `LaneBoard`（第11章）是观测性的基础设施。`SessionHeartbeat` 检测会话是否僵死，`LaneBoard` 汇总所有子任务的状态。传统系统中这些监控是可选的附加组件，在 Agent 系统中它们是核心运行时的一部分——没有观测就无法干预非确定性行为。

`MockParityHarness`（第13章）的 12 个端到端场景也是观测性的体现。不是测试某个函数的输入输出，而是验证整个工作流的行为模式。场景名称如 `bash_permission_prompt_approved` 描述的是用户交互路径，而不是函数调用路径。测试从验证"函数返回正确值"转向验证"用户获得正确体验"。

## 15.3 从"模块化"到"可组合契约"

传统模块化追求高内聚低耦合，模块通过接口定义契约。Agent 系统的模块化需要增加一层"可组合契约"——模块不仅要定义接口，还要定义意图模板和边界策略。

claw-code 的 `ToolSpec`（第6章）是工具的可组合契约：名称、描述、输入 schema、权限要求。模型通过描述和 schema 理解工具的用途，通过权限要求理解工具的边界。工具不是孤立的函数，而是可以被模型理解和组合的意图原子。

`McpToolInfo`（第12章）扩展了这种契约到外部系统——MCP 服务器暴露的工具同样遵循名称 + 描述 + schema 的契约。Agent 工程师设计 MCP 服务器时，不仅需要提供 API 端点，还需要提供清晰的工具描述和精确的输入 schema，否则模型无法正确调用。

`PolicyRule`（第8章）是工作流的可组合契约：`condition` 定义触发条件，`action` 定义响应动作。Lane 工作流（第11章）通过组合这些规则实现自动化流程。传统工作流引擎（如 Airflow）用 DAG 定义流程，Agent 工作流用规则定义条件响应，更适应非确定性环境。

## 15.4 从"调试"到"审计"

传统调试的核心是复现——在本地重现 bug 的输入条件，逐步跟踪执行。Agent 系统的调试面临两个挑战：非确定性使复现困难，多轮对话使状态空间巨大。

claw-code 的会话持久化（第10章）把调试转向审计。JSONL 格式的会话文件完整记录每轮对话，包括消息、工具调用、权限决策和压缩历史。工程师可以事后读取会话文件，分析 Agent 的决策路径，而不是在运行时中断调试。

`SessionCompaction`（第10章）的 `summary` 和 `removed_message_count` 也是审计信息——压缩决策记录了哪些历史被保留、哪些被摘要。如果 Agent 在压缩后行为异常，可以检查摘要是否丢失了关键上下文。

`HookProgressEvent`（第9章）的 `Started`/`Completed`/`Cancelled` 事件提供了钩子执行的审计轨迹。传统日志是文本流，Agent 系统的审计需要结构化的事件序列——每个事件包含事件类型、工具名、命令和状态。

## 15.5 安全边界的重新定义

传统安全模型基于身份和权限——用户有什么角色，角色能访问什么资源。Agent 系统的安全模型基于操作和上下文——Agent 尝试什么操作，操作在当前上下文中是否安全。

claw-code 的 `PermissionMode`（第8章）不是基于用户身份，而是基于操作类型。`ReadOnly` 模式限制的是操作（读取 vs 写入），而不是用户。`classify_bash_permission`（第6章）动态分类命令——`ls` 是只读的，`git status` 是只读的，`rm` 是危险的。权限判断基于命令语义，而不是用户组。

`TrustResolver`（第8章）引入了工作区信任概念——不是问"你是谁"，而是问"你在这个目录中可信吗"。这与传统操作系统的用户权限模型不同，更接近容器和沙箱的安全哲学。

Agent 工程师需要设计"上下文感知的安全策略"——同样的命令在不同上下文中可能有不同的风险。`check_file_write`（第8章）中的 `is_within_workspace` 就是上下文感知——工作区内的写入是允许的，工作区外的写入需要更高权限。

## 15.6 测试范式的转移

传统测试验证"给定输入 X，输出必然是 Y"。Agent 测试验证"给定意图 I，行为模式 B 是可接受的"。

`MockParityHarness`（第13章）的 12 个场景不是测试具体输出，而是测试行为模式：

`read_file_roundtrip` 验证"模型请求读取文件 → 系统执行读取 → 结果返回模型 → 模型基于内容回应"的完整往返。不验证具体读了什么文件，也不验证模型说了什么，只验证流程是否完整。

`bash_permission_prompt_approved` 验证"用户输入 y 后权限被批准 → 命令执行 → 结果返回"。测试的是交互流程，不是命令输出。

这种测试范式更接近行为驱动开发（BDD），但粒度更细——每个场景是一个完整的用户-系统交互回合，而不是单个功能点。Agent 工程师需要把测试看作"验证系统能正确响应用户意图"，而不是"验证函数返回正确值"。

## 小结

从传统工程师到 Agent 工程师的转型涉及五个核心维度。代码从手工产物变为意图的自动展开，工程师需要学习半结构化意图表达（权限规则、工具描述、钩子命令）。确定性让位于可观测性，僵死检测、状态看板和端到端场景成为基础设施。模块化扩展为可组合契约，工具规范、策略规则和工作流定义都服务于模型的理解和组合。调试转向审计，会话持久化、压缩记录和事件轨迹提供事后分析能力。安全边界基于操作和上下文，而非身份和角色。测试验证行为模式而非具体输出，端到端场景取代单元断言。

claw-code 的架构设计（权限系统、钩子系统、会话持久化、MCP 协议、测试 harness）直接支持这些转型。理解架构的意图比理解实现细节更重要——每个模块的存在都是为了解决 Agent 系统特有的不确定性、可观测性和安全挑战。
