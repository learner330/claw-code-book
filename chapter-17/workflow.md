# 第17章 AI-Native 工程工作流

## 本章概览

本章讨论 claw-code 作为基础设施如何融入日常软件工程工作流。不是分析具体代码，而是分析 Agent 协作模式如何改变需求分析、设计评审、编码实现、测试验证和代码审查五个传统阶段。

## 17.1 需求分析：从文档到对话

传统需求分析产出 PRD（产品需求文档）或用户故事。AI-Native 工作流中，需求分析变成与 Agent 的对话——工程师描述意图，Agent 提问澄清，逐步细化需求边界。

claw-code 的会话持久化（第10章）支持这种对话的延续性。`SessionStore` 按工作区分隔离会话，工程师可以在不同项目间切换而不丢失上下文。`prompt_history` 记录用户输入历史，`/resume` 命令恢复之前的会话。这意味着需求分析可以分多次进行——第一次对话确定范围，第二次对话细化边界，第三次对话讨论异常场景。

`compact_session` 自动压缩（第10章）解决对话过长的问题。当 token 超过阈值时，旧消息被压缩为摘要，保留最近 4 条消息。这允许需求分析对话无限延续——只要最近的上下文足够，模型可以理解当前讨论的焦点。

## 17.2 设计评审：从会议到规则

传统设计评审是会议形式——工程师讲解方案，同事提问和质疑。AI-Native 工作流中，设计评审可以转化为权限规则和钩子约束。

claw-code 的 `PermissionPolicy`（第8章）允许工程师在 `settings.json` 中定义设计约束：

```json
{
  "permissions": {
    "deny": ["bash(rm*)", "bash(sudo *)"],
    "ask": ["bash(docker *)"]
  }
}
```

这些规则相当于设计评审的结论——"不允许删除命令"、"Docker 操作需要确认"。规则在每次工具调用前自动评估，不需要人工审查每一行代码。权限规则的可组合性（allow + deny + ask）允许复杂的设计约束表达。

`HookRunner`（第9章）的 `PreToolUse` 钩子可以在执行前做额外检查：

```bash
#!/bin/bash
# ~/.claw/hooks/pre-tool-use.sh
if [ "$HOOK_TOOL_NAME" = "Bash" ]; then
  echo '{"systemMessage":"请注意：bash 命令将在生产环境中执行"}'
fi
```

这个钩子不改变权限决策，但追加系统消息提醒模型注意环境。这相当于设计评审中的提醒——在编码阶段自动触发，而不是依赖工程师记忆。

## 17.3 编码实现：从手工到迭代

传统编码是工程师手工编写代码，IDE 提供补全和重构辅助。AI-Native 编码是 Agent 自动生成代码，工程师提供反馈和纠正。

claw-code 的 `Turn Loop`（第7章）是这种迭代模式的引擎：`run_turn` 循环中，模型生成工具调用（`read_file`、`write_file`、`bash`），系统执行工具并返回结果，模型基于结果生成下一步。这个循环可能持续多轮——模型读取文件、分析内容、写入修改、运行测试、读取测试结果、修复错误。

`build_assistant_message` 的 `std::mem::take` 优化（第7章）支持这种迭代——零拷贝地把文本块刷入消息，减少每轮迭代的开销。`maybe_auto_compact` 在 token 超过阈值时自动压缩历史，防止长对话导致性能下降。

工程师的角色从"编写代码"转变为"定义迭代方向"。当模型陷入循环（反复修改同一文件但无法修复），工程师可以发送新提示调整策略——"先写测试再修改实现"或"检查依赖关系"。`Session` 的 `prompt_history` 记录这些干预，事后可以分析模型的行为模式和工程师的干预策略。

## 17.4 测试验证：从断言到场景

传统测试是断言驱动——验证函数 f(x) 返回预期值。AI-Native 测试是场景驱动——验证 Agent 在特定意图下产生可接受的行为。

claw-code 的 `MockParityHarness`（第13章）是场景驱动测试的示例。12 个场景覆盖核心用户工作流：文件读取、grep 搜索、写入权限、bash 执行、权限提示、插件工具、自动压缩、token 报告。每个场景不是验证单个函数，而是验证完整的交互模式。

工程师在项目中可以定义类似的场景测试。例如，为"添加新 API 端点"定义场景：

1. 模型读取现有路由文件
2. 模型创建新控制器文件
3. 模型写入路由注册
4. 模型运行测试验证路由可访问
5. 模型返回结果

这个场景可以用 `MockAnthropicService` 模拟——定义特定的请求序列和响应模式，验证 Agent 的自动行为是否符合预期。这比传统单元测试更粗粒度，但覆盖了整个工作流。

`compat-harness`（第13章）的源码审计功能可以定期运行——提取 upstream 的 TypeScript 工具清单，对比 Rust 实现的工具覆盖。如果 upstream 新增工具，审计报告会提示工程师更新实现。

## 17.5 代码审查：从 diff 到会话审计

传统代码审查是审查 diff——同事逐行检查代码变更。AI-Native 代码审查可以审查会话审计——分析 Agent 的决策路径和工具调用序列。

`Session` 的 JSONL 持久化（第10章）提供审计基础。每轮对话、每次工具调用、每次权限决策都被记录。工程师可以审查这些记录：

- 模型是否正确使用了工具（如 `read_file` 而不是 `glob_search` 查找单个文件）
- 权限决策是否合理（如 `write_file` 是否被正确允许或拒绝）
- 是否有不必要的工具调用（如反复读取同一文件）

`LaneBoard`（第11章）提供的任务看板可以用于审查并行任务的状态。如果 Agent 启动了多个子任务（通过 `TeamCreate`），工程师可以查看每个任务的心跳状态和完成度，判断任务分配是否合理。

`SessionCompaction` 记录压缩历史——如果模型在压缩后丢失上下文导致错误，可以检查 `summary` 是否遗漏了关键信息。这帮助工程师优化提示策略，避免压缩导致的上下文丢失。

## 17.6 持续集成：从 CI 到 Agent 编排

传统 CI 是预定义脚本的自动执行——编译、测试、打包、部署。AI-Native CI 可以是 Agent 编排的自动执行——Agent 根据代码变更决定测试策略、根据测试结果决定修复策略、根据部署状态决定回滚策略。

`CronRegistry`（第11章）支持周期性任务——可以配置定时检查任务，如"每小时检查代码库状态，报告未提交变更"。`TaskRegistry` 支持子任务管理——CI 流程可以分解为多个子任务（编译任务、测试任务、安全扫描任务），每个任务由独立的 Agent 执行，通过 `LaneBoard` 监控整体状态。

`PolicyEngine`（第8章）的规则可以用于 CI 决策——例如"如果 Green Contract 未满足，阻止合并"、"如果分支超过 1 小时未更新，标记为 stale"。这些规则在 CI 环境中自动执行，不需要人工审批。

## 小结

AI-Native 工程工作流把 claw-code 的各模块串联为完整的工作基础设施。需求分析通过会话持久化和自动压缩支持长期对话。设计评审通过权限规则和钩子约束实现自动化约束。编码实现通过 Turn Loop 的迭代模式实现自动生成和修正。测试验证通过场景驱动测试和源码审计覆盖工作流。代码审查通过会话审计和任务看板提供决策透明度。持续集成通过 Cron 和 Task 编排实现自动化流程。

每个阶段的转变都有一个共同特征：人类从"执行者"变为"设计者和监督者"，Agent 从"辅助工具"变为"执行主体"，系统从"被动平台"变为"主动约束"。claw-code 的架构设计正是为了支撑这种角色转移——权限系统定义约束边界，会话系统记录执行轨迹，测试系统验证行为模式，协调系统编排并行任务。

下一章将总结全书，展望从 claw-code 到 clawable 的演进方向。
